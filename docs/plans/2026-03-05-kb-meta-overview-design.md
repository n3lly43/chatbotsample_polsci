# KB Meta Overview — Design Document

**Date:** 2026-03-05
**Status:** Approved — Implementation verified, 125/125 tests passing

## Problem

When users ask meta-questions about the knowledge base — "What kind of data do you have?", "What datasets are available?", "What is in the knowledge base?" — the system returns zero results and refuses to answer.

**Root cause:** Vector search matches user queries against specific document chunks by embedding similarity with a `max_distance` threshold (0.55). Abstract meta-questions like "what data is available" are semantically distant from any specific chunk content (PTS scores, country data, methodology text). All candidate chunks exceed the distance threshold and are filtered out. Layer 0 (no-source refusal) then blocks the LLM from being called.

**Secondary problem:** The LLM has no awareness of the knowledge base's overall structure. Even when answering specific questions, it cannot contextualize its answer within the broader KB. For example, it cannot say "the PTS dataset, one of three datasets in the knowledge base, shows..." because it only sees the retrieved chunks, not the whole picture.

## Solution

Generate a **KB meta overview** during ingestion — an LLM-produced high-level summary describing what documents and tables exist, what topics they cover, and how they connect. This overview is used three ways:

1. **ChromaDB chunk** — Stored as a special chunk so meta-questions find it via vector search (solves the retrieval gap)
2. **QU prompt injection** — Gives the query understanding LLM full KB awareness for better routing and reformulation
3. **System prompt injection** — Gives the response LLM the "general picture" for better-contextualized answers

## Architecture

```
Ingestion pipeline (after all files + SQL tables are processed):
    |
    v
collect_file_records(collection)     # scan ChromaDB metadata
collect_sample_chunks(collection)    # get first chunk per document
load_sql_schema(cfg)                 # get SQL table schemas
    |
    v
generate_kb_overview_with_llm()      # LLM analyzes content + connections
    |                                 # Falls back to deterministic listing
    v
Three outputs:
    1. save_kb_meta()                 # chroma_db/kb_meta.txt (file)
    2. upsert_meta_chunk()            # ChromaDB special chunk
    3. (loaded at query time by query_engine.py and verifier.py)
```

### Query-time data flow

```
User query
    |
    v
Query Understanding (loads kb_meta.txt)
    | KB overview injected into QU prompt
    | -> LLM knows full KB contents for routing/reformulation
    |
    v
Retriever (unchanged)
    | For meta-questions: meta chunk is found via vector search
    | For specific questions: normal retrieval
    |
    v
verify_and_respond (loads kb_meta.txt)
    | KB overview injected into system prompt
    | -> LLM has "general picture" alongside specific chunks
    |
    v
Cited response
```

## Design Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Overview generation | **LLM-powered with deterministic fallback** | LLM can describe document topics, identify connections between datasets. Deterministic fallback (file listing) if LLM fails. |
| Overview storage | **File + ChromaDB chunk** | File: fast loading at query time, no ChromaDB dependency. Chunk: enables vector search to find the overview for meta-questions. |
| Overview injection points | **QU prompt + system prompt** | QU: better routing (knows what's available). System: better answers (sees the big picture). Both are small token costs (~200-400 words). |
| When to generate | **At end of ingestion** | Overview changes only when documents change. One-time LLM call per ingestion, not per query. |
| Meta chunk source name | **"Knowledge Base Overview"** | Clean citation if the LLM cites the overview. Skipped by `collect_file_records()` to avoid self-reference. |

## Meta Overview Content

### LLM-generated (primary path)

The LLM receives:
- **Document inventory**: File names, types, datasets, chunk counts
- **Sample content**: First chunk from each document (~500 chars each)
- **SQL table schemas**: Table names, columns, row counts

It produces a 200-400 word overview covering:
1. **What is in the knowledge base**: Each document/dataset with a 1-sentence description
2. **Key topics and themes**: What subjects the KB covers
3. **Connections**: How documents/datasets relate (shared countries, time periods, variables)

### Deterministic fallback

If the LLM call fails, a structured listing is generated:
- Documents grouped by dataset with file types and chunk counts
- SQL tables with column lists and row counts
- Basic connection note ("all datasets are part of the same knowledge base")

## File Locations

| File | Path | Generated by | Read by |
|---|---|---|---|
| Overview text | `chroma_db/kb_meta.txt` | `src/kb_meta.py` at ingestion | `query_engine.py`, `verifier.py` at query time |
| Meta chunk | ChromaDB collection (id: `kb_meta_overview_001`) | `src/kb_meta.py` at ingestion | `retriever.py` via normal vector search |

## Integration Points

### `src/ingest.py` — Trigger

After all document chunks + SQL tables are ingested, calls `build_and_store_overview(collection, cfg)`. Non-fatal: wrapped in try/except so overview failure doesn't block ingestion.

### `src/prompts.py` — Template changes

**System prompt** (`SYSTEM_PROMPT_TEMPLATE`): New `{kb_overview_section}` placeholder between RESPONSE LENGTH and CONTEXT sections. When present, adds a "KNOWLEDGE BASE OVERVIEW" section marked "do NOT cite this section directly."

**QU prompt** (`QUERY_UNDERSTANDING_PROMPT_TEMPLATE`): New `{kb_overview_block}` placeholder before CONVERSATION HISTORY. Shows "KNOWLEDGE BASE CONTENTS (use this to understand what is available)."

**`build_prompt()`**: Gains optional `kb_overview: str = ""` parameter. Backward compatible.

**`build_query_understanding_prompt()`**: Gains optional `kb_overview: str = ""` parameter. Backward compatible.

### `src/query_engine.py` — Load and pass

Loads `kb_meta.txt` via `load_kb_meta(cfg)` and passes to `build_query_understanding_prompt()`. Only runs when QU is enabled (disabled path returns early before this).

### `src/verifier.py` — Load and pass

Loads `kb_meta.txt` via `load_kb_meta(cfg)` and passes to `build_prompt()`. Only runs when sources exist (Layer 0 check returns before this).

### `src/retriever.py` — No changes

The meta chunk is retrieved via normal vector search. `format_db_results_as_context()` formats it like any other chunk. No special handling needed.

## Graceful Degradation

| Scenario | Behavior |
|---|---|
| No `kb_meta.txt` (first run, or ingestion skipped) | `load_kb_meta()` returns `""` → overview sections omitted from prompts → identical to pre-feature behavior |
| LLM call fails during overview generation | Falls back to deterministic overview (file listing) |
| ChromaDB meta chunk upsert fails | Overview still saved as file; QU and system prompts still get the overview; only vector search for meta-questions is affected |
| Empty knowledge base | `build_and_store_overview()` returns `""` → no file, no chunk → no impact |
| `kb_meta.txt` corrupted | `load_kb_meta()` catches exception, returns `""` → no impact |

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| LLM overview adds cost at ingestion time | Single call (~1K output tokens). Runs once per `python ingest.py`, not per query. |
| Overview text bloats prompt tokens at query time | Capped at 200-400 words (~300-500 tokens). Small relative to context budget. |
| Overview becomes stale if KB changes without re-ingestion | Same as existing behavior: ChromaDB/SQLite are stale until re-ingestion. Overview regenerates with every `python ingest.py`. |
| Meta chunk contaminates normal retrieval | Low risk: the chunk's content is genuinely about the KB, so it should only match meta-questions. Source name `"Knowledge Base Overview"` is descriptive. |
| Double-brace escaping in LLM output | Pre-existing codebase pattern. `_escape_braces()` applied to overview text before `str.format()`. Cosmetic `{{}}` in output; LLM can still understand. |
